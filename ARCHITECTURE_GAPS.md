# Mushin Lite — Architecture Gap Register

**Status:** Draft for review
**Companion:** `ARCHITECTURE.md` (target architecture)
**Purpose:** Record observed differences between the target architecture and Mushin Lite, without redefining the target.

## Interpretation and change control

- **The architecture contract is authoritative.** This register describes implementation status; it does not weaken or replace any invariant.
- **A gap is not automatically a defect or an instruction to refactor.** Lite is a limited reference implementation, and target features may be intentionally deferred.
- **Documentation is not implementation authorization.** No code changes, new dependencies, or architectural migrations are approved by this register.
- Entries marked **Observed** are supported by the inspected `master` source files. **Partial** means some relevant mechanisms exist but full conformity has not been demonstrated. **Not demonstrated** means the review did not establish that a mechanism exists; it does not prove absence. **Future target** means explicitly planned capability, not a failure of the prototype.
- Evidence below was rechecked against `master` at `150cabbf5a08333e31691df8242c31be238af4b9` (`Fix disabled local conditioning fallback`). Source inspection covers the relevant functions in `main.py`, `behavior.py`, `collapse.py`, `canon.py`, `renderer.py`, `world.py`, `packet_interpreter.py`, `rules.py`, `llm_adapter.py`, `npc_fixture.py`, and `map_data.py`. This is not an exhaustive runtime, concurrency, crash-durability, or test audit. Recheck the revision before authorizing engineering work.
- **Contract clarifications** belong in `ARCHITECTURE.md`; **observed implementation deviations**, **unimplemented future architecture**, and **open design questions** are distinguished below. A demonstrated local safeguard does not establish system-wide conformity.

## Audience disclosure architecture checkpoint

Reviewed against `a64e14caddefe0cb719f47c599f765c059f7ac7c`. The new §3 disclosure contract is **specified only**; no runtime path is changed or certified audience-safe by this checkpoint. Local command interpretation still receives every active fact, presentation retains active canon, NPC inquiries print transition diagnostics, and developer commands share the ordinary CLI. G-03/G-04 therefore remain open.

Integration cannot safely stop at excluding NPC event text. At that checkpoint, `main.handle_observation_command` dropped discovery provenance and committed reveal/marker separately through `canon.add_fact`, which mutates memory before persistence. The observation slice below replaces that loop with independent atomic commitment; persistent acquisition provenance is still absent. The approved §3 decision requires revelation, collapse marking, and independently authorized player acquisition in one atomic snapshot; this extension is unimplemented. The exact acquisition schema and shared-envelope integration are approved in §3 but remain unimplemented. Source/reference binding and freshness remain independent authorization requirements. Ordinary turn-local action results need a bounded typed handoff; arbitrary text cannot grant disclosure. Existing reset paths must atomically clear affected grants and rotate generations so identical recreated IDs/content cannot inherit them. These changes require focused ordinary-gameplay and failure regression coverage in addition to the existing NPC suites.

The next production checkpoint must implement and test records/authorization/reset behavior and the observation/action compatibility contracts, then wire all player model/presentation entry points and separate diagnostics. Until that integration passes its acceptance gate, do not claim offscreen simulation is player-safe. Missing legacy acquisition evidence must not be repaired by classifying active facts as public. General testimony, witnessing, beliefs, sensory simulation, and free-form prose verification remain deferred.

## Shared disclosure validation foundation

Implementation based on `cb6e014`: `disclosure_rules` provides pure canonical JSON/SHA-256 helpers, strict decoding for disclosure-bearing saves, exact envelope/variant/source validation, generation and historical reference checks, per-record diagnostics, duplicate-record rejection, and identical-valid-record recognition. `inspect_disclosure` distinguishes absent, valid, malformed, unsupported, and invalid-reference storage; structural failures suppress all valid indices, while individually broken references retain unaffected valid indices but block recognition for future writes. Results are internal validation diagnostics, not presentation or acquisition authorization. Historical checks use committed facts/keyed NPC outcomes and do not consult current providers, inquiry bindings, or observation configuration.

`canon.load_state` validates disclosure before legacy status defaults, rejecting inconsistent storage without rewriting the file or creating generations/records. Saves without the extension retain their existing loading behavior. `test_disclosure.py` adds 26 standard-library tests; full discovery passes 140 tests including all 114 existing regressions. Coverage includes exact encoding/digest payloads, mixed records, identities, versions, generation mismatch, missing/duplicate/changed references, historical statuses, provider removal, idempotent recognition, purity/import isolation, and load preservation/rejection.

This foundation does not authorize new acquisitions or make gameplay audience-safe. Digests validate consistency of trusted canon-owned records, not malicious save editing or historical permissions reconstructed from a configuration fingerprint. Reset generation rotation, write-boundary/pre-sampling integration, atomic observation acquisition, separate truthful-inquiry disclosure commitment, and player-context filtering remain unimplemented. Existing reset/developer write paths are unchanged and must not be used as evidence of disclosure lifecycle safety. G-03/G-04/G-08/G-15 remain open; the next integration boundary is authorized acquisition and its generation/reset lifecycle, with current observation and NPC resolution semantics preserved.

## Selective-forgetting protection checkpoint

Approved against `d28ceb9`, **not implemented**: §3 now requires ordinary selective deletion/resolution to preserve committed observation collapse markers, including legacy markers without acquisitions. Selective deletion must reject invalidation of valid acquisition references; legitimate supersession/resolution of ordinary referenced reveal/event facts remains allowed under existing historical status and digest checks. Acquisition records must not be silently removed to bypass protection. Only an explicitly authorized reset may remove protected history within its declared scope, with canonical/disclosure/generation changes persisted atomically before caller-memory update and explicit reconciliation after uncertain writes.

At this checkpoint, `canon.forget_fact` deletes facts and `canon.resolve_fact` changes status without these guards; `observation_rules.observation_candidates` checks active markers, so either operation can reopen a collapsed space. Deleting a disclosed reveal makes `inspect_disclosure` report an invalid reference and `load_state` reject the save. The next lifecycle implementation must add deletion/status guards and full-world/NPC generation-reset integration, preserving unrelated acquisitions and legacy no-reroll behavior. Acceptance must cover protected legacy markers, both acquisition variants, allowed historical status transitions, atomic reset failures, and uncertain-write handling. No tombstones, repair mechanism, new history store, acquisition commitment, or presentation filtering is introduced. G-04 and G-08 remain open.

## Selective history and reset lifecycle implementation

Local implementation based on `c142a36`: `canon.forget_fact` and `resolve_fact` now reject collapse-marker edits even without disclosure data; deletion also rejects references held by valid acquisitions. Both operations validate disclosure before editing and persist detached pending state before caller-memory update. Ordinary referenced reveal/event resolution and existing supersession remain valid under historical checks; no acquisition is deleted to permit a selective edit. Invalid or unsupported disclosure, including broken references, blocks these operations and resets without repair.

`forget_all`, `reset_npc_state`, and `reset_npc_test_fixture` now persist reset history and disclosure changes in one snapshot. Resets initialize absent envelopes with empty records and opaque UUID identities, never reconstructing legacy acquisitions. Full reset clears acquisitions and rotates both generation identities; NPC reset retains world generation, removes only NPC acquisitions, rotates NPC generation, and preserves valid observation history. Pending reference validation rejects any reset that would damage retained acquisitions. Loading remains unchanged and creates no identities. `forget_all` accepts separately trusted setup facts so `/testreset` installs its canonical fixture in that same snapshot; map reset remains a separate write with no cross-store atomicity guarantee.

`test_disclosure_lifecycle.py` adds 21 tests; full discovery passes 161 tests, retaining the prior 140. Evidence covers marker/reference rejection, permitted resolution/supersession, malformed and stale references, legacy loads and first reset initialization, stable reloads, generation rotation/reuse rejection, unrelated acquisition preservation, fixture reset, persistence failures before and after replacement, no automatic retry, CLI rejection, and no observation reroll after rejected edits. Persistence exceptions require reload/reconciliation; the CLI stops on those errors. No durable request identity, concurrent-writer safety, or directory-fsync crash guarantee is added.

The approved guards and bounded reset enforcement above are implemented; the preceding checkpoint records their earlier unimplemented status. General save/developer-write hardening, observation disclosure preflight, atomic observation acquisition, separately authorized NPC inquiry acquisition, and player-context projection remain unfinished. The next acquisition boundary must independently authorize revelation/marker/acquisition in one snapshot, initialize absent generations only in an authorized transaction, and reject inconsistent disclosure before sampling; it must reuse this reset lifecycle without treating existing active facts as knowledge. G-04 and G-08 remain open; this slice grants no acquisitions and does not make gameplay audience-safe.

## Atomic player observation acquisition implementation

Local implementation based on `2db71f6`: `observation_activation.activate_observation` now runs pure disclosure preflight before resolution. `canon.commit_observation` repeats preflight and independently authorizes truth through `observation_rules.validate_observation`; `disclosure_rules.authorize_observation_acquisition` separately rechecks those shared authorization rules against pre-commit state/configuration and verifies the exact newly allocated reveal/marker facts. It derives the fixed player audience, observation provenance, complete configuration fingerprint, and generation-qualified content digest without consulting the producer, renderer, or LLM. No caller-supplied source/grant or arbitrary historical-fact acquisition endpoint is accepted.

The detached observation snapshot now contains reveal, active collapse marker, and the exact version-1 `observation_discovery` record. Absent generation identities are created only for an authorized non-null commitment; existing identities and history are retained. Canon validates pending fact allocation and all disclosure records before a single atomic save and caller-memory update. Rejections and failures return no reveal; uncertain replacement requires reload/reconciliation without automatic retry. Null outcomes create no records or identities; valid repeats and legacy markers do not reroll or backfill acquisition. Broken modern references reject before sampling, including a missing marker; duplicate/unsupported storage is never repaired.

`test_observation_acquisition.py` adds 15 focused tests; full discovery passes 176 tests, retaining the prior 161. Coverage includes the complete snapshot and independently calculated digests, existing NPC history, forged/stale proposals, matching-basis ineligibility, acquisition authorization and pending-validation failure, corrupt preflight, null/legacy behavior, repeat/reload, configuration removal, historical status transitions, and known/uncertain persistence failures. The existing legacy-marker regression now explicitly omits the disclosure extension so it continues testing legacy history rather than treating a damaged modern acquisition as legacy. Existing desk probability, ordinary-action, NPC, and lifecycle tests pass.

This implements the bounded observation acquisition transaction, not audience-safe presentation. No NPC inquiry acquisition, player projection, interpreter/renderer filtering, subjective packets, or general knowledge policy is added. Shared historical validation remains usable without installed observation providers. Existing single-threaded/current-state assumptions, trusted-save digest limits, lack of durable retry identity/directory-fsync guarantees, general developer-write gaps, and separate map persistence remain. Next implement the independently authorized truthful NPC inquiry acquisition transaction; audience projection and filtering must then cover all player-facing paths before claiming offscreen safety. G-03/G-04/G-08/G-15 remain open.

## Ordinary-action and observation authorization contract

At `05fe4d3`, the ordinary CLI normalizes/interprets input, resolves accessible entity references, calls `world.interaction_supported`, constructs facts, then applies rules before looping over `canon.add_fact`. Observation handling verifies room/space/verb upstream; collapse filters candidates, checks markers and existing whereabouts/facts, samples, and returns reveal/marker packets. `add_fact` independently checks neither operation's authority or freshness; it only deduplicates, supersedes, and saves. No ordinary-action probability draw currently occurs.

The local ordinary-action slice based on `ccc12249` implements `canon.commit_player_action` and pure `player_action_rules.validate_player_action`: exact versioned proposal fields, conservative whole-state/configuration freshness, independent eligibility and complete-effect validation, and explicit committed/no-change/rejected/failed results. `world.interaction_supported` accepts separately trusted definitions; `world.action_already_satisfied` shares pure block predicates with upstream rules. Neither a matching basis nor an upstream eligibility flag substitutes for authorization. The CLI routes ordinary actions through this boundary and uses its validated block text; it stops on persistence failure rather than continuing from potentially stale memory.

`test_player_action.py` covers action/alias/target compatibility, movement, rule precedence and consequences, forged/malformed/stale proposals, matching-basis ineligibility, atomic failures, detached results, CLI rejection/failure, provider independence, and historical preservation. Each full action unit is built in a pending snapshot and persisted through existing atomic snapshot infrastructure before caller-memory update. Distinct ordinary-action events receive existing fact IDs without prose deduplication; older events and state-slot supersession remain intact. This exception does not change `add_fact`, NPCs, observations, or developer commands. Fact IDs do not identify retries: an uncertain replacement requires explicit reconciliation, with no automatic retry.

G-02 and G-08 remain open. Observation authorization and atomic reveal/marker commitment are now implemented in the bounded slice below; legacy collapse markers still cannot identify learned content. ## Observation commitment slice

Based on `f56f816`, `canon.commit_observation` accepts the exact §5 proposal and derives effects from separately supplied installed definitions. `observation_rules` validates binding, room presence, unique IDs, explicit constraints, reveal schemas, finite nonnegative weights, eligible positive selections, whereabouts, active reveal facts, collapse markers, and whole-state/configuration freshness. Explicit empty required tags remain valid; missing constraints do not. Configuration validates before sampling. Marker-only legacy history produces no change without inferring a discovery; a null selection cannot replace an available positive-weight discovery, and an eligible zero-total catalogue fails rather than pretending to be empty.

`observation_activation.activate_observation` externally composes validation, `collapse.resolve_observation_candidates`, and commitment. Sampling returns only the discovery ID; commitment neither samples nor calls the producer. The CLI binds against installed room definitions rather than renderer context, presents only committed reveals, rejects without `add_fact` fallback, and stops on persistence failure for reconciliation. The existing desk weights (1:3:2), other installed search/inspect reveals, and active marker guards remain intact. No disclosure record, cause expansion, or historical reveal/marker link is invented. The approved atomic acquisition extension is not implemented by this reveal/marker boundary; legacy markers cannot reconstruct discovery identity or grant knowledge. Null outcomes remain no change without acquisition, and truthful NPC inquiry retains its separate disclosure transaction after episode commitment.

`test_observation.py` covers these boundaries, repeat/reload without draws, known and uncertain persistence failures, independent commitment, and CLI compatibility. Atomicity uses the existing snapshot writer; caller memory changes only after successful persistence. This does not provide durable retry identity, concurrency control, reset-generation identity, directory-fsync crash durability, or audience-safe disclosure. G-02 and G-08 remain open for the other recorded paths and guarantees.

## Important distinctions

### The prototype `behavior.py` is not the complete proposed Behavior expansion

The current file is a bounded NPC episode and transition evaluator. The **Behavior module** described by the contract is a larger optional high-resolution system. Sharing a name must not be treated as evidence that the full architecture exists, or that the file must necessarily be discarded.

### Separation into files is not equivalent to airgapping

The target requires independently composable transformations with declared interfaces. A distinct Python module can still be coupled to another stage through imports, callbacks, or private state access. Conversely, shared non-processing schemas and approved infrastructure are permitted by the contract.

### A future target is not an immediate task

The goal of this document is architectural visibility. Decisions about sequence, implementation design, testing, and changes to code require separate review and authorization.

## Open questions for subsequent architecture work

1. What are the stable data envelopes between the engine and external consumers, and between major internal transformations?
2. How will orchestration expose compatible insertion points without exposing stage internals or making pipeline ordering arbitrary where causality forbids it?
3. Which capabilities are fundamental baseline responsibilities, and which are specialized cartridge/module features that can simply be absent?
4. How can optional Behavior refine the bounded `interaction_v1` baseline under independent authorization without producing a second resolution path?
5. Which schemas and commitment boundaries implement the established distinction among objective truth packets, observer/subjective packets, learned information, authorized presentation, and diagnostics?
6. What state and side effects are allowed for adapters, shared infrastructure, and orchestration code?
7. What are each operation’s freshness dependencies, atomic units, concurrency/crash guarantees, and explicit retry or reconciliation policies?
8. Which shared authorization contracts let commitment validate independently of proposal-producing implementations?
9. How are persisted extension data retained and interpreted when their optional module is absent?
10. Which audience/knowledge policy filters engine output, and how are invalid conditioned results detected or safely replaced?
11. How should future scheduling and opportunity generation extend the explicit-window `initiation_v1` boundary without weakening persistent abstention or claims?
12. What is the operational contract for evidence gravity, preserving its native meaning without guessing a mechanism?

## Maintenance procedure

1. Update `ARCHITECTURE.md` to express the target requirement.
2. Reassess any affected gap entry here; mark observations with the repository revision or tests used when available.
3. Keep **observed behavior**, **inference**, **future target**, and **open question** distinct.
