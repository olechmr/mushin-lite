# Mushin Lite — Architecture Gap Register

**Status:** Draft for review
**Companion:** `ARCHITECTURE.md` (target architecture)
**Purpose:** Record observed differences between the target architecture and Mushin Lite, without redefining the target.

## Interpretation and change control

- **The architecture contract is authoritative.** This register describes implementation status; it does not weaken or replace any invariant.
- **A gap is not automatically a defect or an instruction to refactor.** Lite is a limited reference implementation, and target features may be intentionally deferred.
- **Documentation is not implementation authorization.** No code changes, new dependencies, or architectural migrations are approved by this register.
- Entries marked **Observed** are supported by the inspected `master` source files. **Partial** means some relevant mechanisms exist but full conformity has not been demonstrated. **Not demonstrated** means the review did not establish that a mechanism exists; it does not prove absence. **Future target** means explicitly planned capability, not a failure of the prototype.
- Evidence below was rechecked against `master` at `150cabbf5a08333e31691df8242c31be238af4b9` (`Fix disabled local conditioning fallback`). Source inspection covers the relevant functions in `main.py`, `behavior.py`, `collapse.py`, `canon.py`, `renderer.py`, `world.py`, `packet_interpreter.py`, `rules.py`, `llm_adapter.py`, `npc_fixture.py`, and `map_data.py`. This is not an exhaustive runtime, concurrency, crash-durability, or test audit. Recheck the revision before authorizing engineering work.
- **Contract clarifications** belong in `ARCHITECTURE.md`; **observed implementation deviations**, **unimplemented future architecture**, and **open design questions** are distinguished below. A demonstrated local safeguard does not establish system-wide conformity.

## Audience disclosure architecture checkpoint

Reviewed against `a64e14caddefe0cb719f47c599f765c059f7ac7c`. The new §3 disclosure contract is **specified only**; no runtime path is changed or certified audience-safe by this checkpoint. Local command interpretation still receives every active fact, presentation retains active canon, NPC inquiries print transition diagnostics, and developer commands share the ordinary CLI. G-03/G-04 therefore remain open.

Integration cannot safely stop at excluding NPC event text. At that checkpoint, `main.handle_observation_command` dropped discovery provenance and committed reveal/marker separately through `canon.add_fact`, which mutates memory before persistence. The observation slice below replaces that loop with independent atomic commitment; persistent acquisition provenance is still absent. Persistent acquisitions require a documented atomic observation unit and independently authorized source/reference binding. Ordinary turn-local action results need a bounded typed handoff; arbitrary text cannot grant disclosure. Existing reset paths must atomically clear affected grants and rotate generations so identical recreated IDs/content cannot inherit them. These changes require focused ordinary-gameplay and failure regression coverage in addition to the existing NPC suites.

The next production checkpoint must implement and test records/authorization/reset behavior and the observation/action compatibility contracts, then wire all player model/presentation entry points and separate diagnostics. Until that integration passes its acceptance gate, do not claim offscreen simulation is player-safe. Missing legacy acquisition evidence must not be repaired by classifying active facts as public. General testimony, witnessing, beliefs, sensory simulation, and free-form prose verification remain deferred.

## Ordinary-action and observation authorization contract

At `05fe4d3`, the ordinary CLI normalizes/interprets input, resolves accessible entity references, calls `world.interaction_supported`, constructs facts, then applies rules before looping over `canon.add_fact`. Observation handling verifies room/space/verb upstream; collapse filters candidates, checks markers and existing whereabouts/facts, samples, and returns reveal/marker packets. `add_fact` independently checks neither operation's authority or freshness; it only deduplicates, supersedes, and saves. No ordinary-action probability draw currently occurs.

The local ordinary-action slice based on `ccc12249` implements `canon.commit_player_action` and pure `player_action_rules.validate_player_action`: exact versioned proposal fields, conservative whole-state/configuration freshness, independent eligibility and complete-effect validation, and explicit committed/no-change/rejected/failed results. `world.interaction_supported` accepts separately trusted definitions; `world.action_already_satisfied` shares pure block predicates with upstream rules. Neither a matching basis nor an upstream eligibility flag substitutes for authorization. The CLI routes ordinary actions through this boundary and uses its validated block text; it stops on persistence failure rather than continuing from potentially stale memory.

`test_player_action.py` covers action/alias/target compatibility, movement, rule precedence and consequences, forged/malformed/stale proposals, matching-basis ineligibility, atomic failures, detached results, CLI rejection/failure, provider independence, and historical preservation. Each full action unit is built in a pending snapshot and persisted through existing atomic snapshot infrastructure before caller-memory update. Distinct ordinary-action events receive existing fact IDs without prose deduplication; older events and state-slot supersession remain intact. This exception does not change `add_fact`, NPCs, observations, or developer commands. Fact IDs do not identify retries: an uncertain replacement requires explicit reconciliation, with no automatic retry.

G-02 and G-08 remain open. Observation authorization and atomic reveal/marker commitment are now implemented in the bounded slice below; legacy collapse markers still cannot identify learned content. Durable request identity, disclosure provenance/reset generations, cross-store map consistency, and concurrency remain separate work. No history reconstruction, scheduler, or generalized cartridge system is introduced.

## Observation commitment slice

Based on `f56f816`, `canon.commit_observation` accepts the exact §5 proposal and derives effects from separately supplied installed definitions. `observation_rules` validates binding, room presence, unique IDs, explicit constraints, reveal schemas, finite nonnegative weights, eligible positive selections, whereabouts, active reveal facts, collapse markers, and whole-state/configuration freshness. Explicit empty required tags remain valid; missing constraints do not. Configuration validates before sampling. Marker-only legacy history produces no change without inferring a discovery; a null selection cannot replace an available positive-weight discovery, and an eligible zero-total catalogue fails rather than pretending to be empty.

`observation_activation.activate_observation` externally composes validation, `collapse.resolve_observation_candidates`, and commitment. Sampling returns only the discovery ID; commitment neither samples nor calls the producer. The CLI binds against installed room definitions rather than renderer context, presents only committed reveals, rejects without `add_fact` fallback, and stops on persistence failure for reconciliation. The existing desk weights (1:3:2), other installed search/inspect reveals, and active marker guards remain intact. No disclosure record, cause expansion, or historical reveal/marker link is invented.

`test_observation.py` covers these boundaries, repeat/reload without draws, known and uncertain persistence failures, independent commitment, and CLI compatibility. Atomicity uses the existing snapshot writer; caller memory changes only after successful persistence. This does not provide durable retry identity, concurrency control, reset-generation identity, directory-fsync crash durability, or audience-safe disclosure. G-02 and G-08 remain open for the other recorded paths and guarantees.

## Important distinctions

### The prototype `behavior.py` is not the complete proposed Behavior expansion

The current file is a bounded NPC episode and transition evaluator. The **Behavior module** described by the contract is a larger optional high-resolution system. Sharing a name must not be treated as evidence that the full architecture exists, or that the file must necessarily be discarded.

### Separation into files is not equivalent to airgapping

The target requires independently composable transformations with declared interfaces. A distinct Python module can still be coupled to another stage through imports, callbacks, or private state access. Conversely, shared non-processing schemas and approved infrastructure are permitted by the contract.

### A future target is not an immediate task

The goal of this document is architectural visibility. Decisions about sequence, implementation design, testing, and changes to code require separate review and authorization.

## Open questions for subsequent architecture work

1. What are the stable data envelopes between the engine and external consumers, and between major internal transformations?
2. How will orchestration expose compatible insertion points without exposing stage internals or making pipeline ordering arbitrary where causality forbids it?
3. Which capabilities are fundamental baseline responsibilities, and which are specialized cartridge/module features that can simply be absent?
4. How can optional Behavior refine the bounded `interaction_v1` baseline under independent authorization without producing a second resolution path?
5. Which schemas and commitment boundaries implement the established distinction among objective truth packets, observer/subjective packets, learned information, authorized presentation, and diagnostics?
6. What state and side effects are allowed for adapters, shared infrastructure, and orchestration code?
7. What are each operation’s freshness dependencies, atomic units, concurrency/crash guarantees, and explicit retry or reconciliation policies?
8. Which shared authorization contracts let commitment validate independently of proposal-producing implementations?
9. How are persisted extension data retained and interpreted when their optional module is absent?
10. Which audience/knowledge policy filters engine output, and how are invalid conditioned results detected or safely replaced?
11. How should future scheduling and opportunity generation extend the explicit-window `initiation_v1` boundary without weakening persistent abstention or claims?
12. What is the operational contract for evidence gravity, preserving its native meaning without guessing a mechanism?

## Maintenance procedure

When an architectural decision is approved:

1. Update `ARCHITECTURE.md` to express the target requirement.
2. Reassess any affected gap entry here; mark observations with the repository revision or tests used when available.
3. Keep **observed behavior**, **inference**, **future target**, and **open question** distinct.
4. Do not modify code merely to make this register look complete.
5. Treat implementation proposals, test plans, and commits as separately authorized work.

**Review conclusion at `150cabb`:** Mushin Lite exhibits important foundations for canonical-state authority and bounded NPC evaluation, but the target's general-purpose stage isolation, module composition, application-level decoupling, and archetype fallback are not yet established by the inspected implementation.
